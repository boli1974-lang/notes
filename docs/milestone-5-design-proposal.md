# Phase 1 — Milestone 5: Design Proposal (Prisma + Service API)

**Status:** Updated per review; final Prisma and service interfaces at end of document.

---

## 1. Storage visibility and URL generation

- **Bucket visibility:** **Private.** The Supabase Storage bucket for note images is private. Images must **not** be publicly accessible.
- **Image display:** All images are displayed using **signed URLs generated by the server**. The API returns only signed URLs (no direct public URLs).
- **Where URLs are created:** Signed URLs are generated in the **service layer** (`noteImageService.listImagesByNoteId`), not in the repository. The storage wrapper exposes `createSignedUrl(path, expiry)`; the service calls it and attaches the URL to each image record before returning.

---

## 2. Upload during note creation

Users can attach images **before the note is saved**. Implementation follows this model.

**Create flow (new note):**

1. User selects images in the UI → images are stored in **local UI state only** (e.g. `File` objects or draft list).
2. Previews use **`URL.createObjectURL`**; no server upload yet.
3. Images are **not uploaded** until the user clicks **Save note**.

**When the user clicks Save note (new note):**

1. **Create the note** (POST note first).
2. **If note creation fails** → do **not** upload any images; show error to user.
3. **If note creation succeeds** → for each draft image, upload to storage and create `NoteImage` metadata row.
4. **If note creation succeeds but one or more image uploads fail** → the note remains created; UI reports which uploads failed (e.g. per-image error messages or a summary). No rollback of the note.

**Edit flow (existing note):** User adds images in edit mode; on Save, upload new images and create metadata. Same partial-failure rule: note/title/content/tags are already saved; image upload failures are reported without undoing the note update.

**Upload API shape:** `POST /api/notes/[id]/images` is **single-file-per-request**. The API accepts one multipart file per request. The UI loops and calls the API once per image to upload multiple images.

## 3. Prisma model: `NoteImage`

```prisma
model NoteImage {
  id          String    @id @default(uuid()) @db.Uuid
  noteId      String    @db.Uuid
  storagePath String    @db.VarChar(512)   // full path in bucket: notes/{noteId}/{uuid}-{fileName}
  fileName    String    @db.VarChar(255)   // original filename for display
  contentType String   @db.VarChar(128)   // e.g. image/jpeg, image/png, image/webp
  sizeBytes   Int
  createdAt   DateTime  @default(now())
  deletedAt   DateTime?
  userId      String?   @db.Uuid

  note Note @relation(fields: [noteId], references: [id], onDelete: Cascade)

  @@index([noteId])
  @@index([deletedAt])
  @@index([userId])
}
```

**Note model:** add relation `noteImages NoteImage[]`.

**Field rationale:** See table in original proposal (id, noteId, storagePath, fileName, contentType, sizeBytes, createdAt, deletedAt, userId). **Cascade:** `onDelete: Cascade` for note hard-delete; soft-delete of note is handled in app logic.

## 4. Image delete behavior

Image-level delete is **final** after Save (not recoverable).

**During edit mode:**

- **Existing images** (already on server): can be marked **pendingDelete** in UI state; nothing is persisted until Save.
- **Newly added draft images** (not yet uploaded): can be **removed immediately** from draft state; no server call.

**On Save (when user confirmed pending deletes):**

1. **Storage:** Delete the storage object (hard delete).
2. **DB:** Metadata row is **soft deleted** (`softDeleteImage`); we do **not** hard-delete the metadata row.

Repository consistently uses **softDeleteImage** (and **softDeleteImagesByNoteId** for note-level) — no hard-delete of metadata in normal flows.

---

## 5. Note delete behavior and Undo

The application supports **toast-based Undo only** (no recycle bin).

**When a note is deleted:**

1. Note row is **soft deleted**.
2. Associated image metadata rows are **soft deleted** (`softDeleteImagesByNoteId`).
3. **Storage objects are NOT deleted immediately.**

**If the user clicks Undo within the toast window:**

- Restore the note (`restoreNote`).
- Restore image metadata (`restoreImagesByNoteId`).

**If the Undo window expires:**

- Storage objects for that note’s images must be **permanently deleted**.
- **Undo-expiry cleanup path (explicit):** When the existing client-side Undo timeout fires, the **UI calls a cleanup API** (e.g. `POST /api/notes/[id]/images/cleanup-after-undo-expiry`). **That API invokes `deleteStorageObjectsForNoteId(noteId)`** on the server. After the API call, the UI clears the pending-deleted state. (Timeout fires → UI calls cleanup API → API calls `deleteStorageObjectsForNoteId(noteId)` → UI clears state.)

## 6. Repository API: `lib/repositories/noteImageRepository.ts`

Naming uses **soft delete** only for metadata; no hard-delete of rows in normal flows.

| Function | Signature | Behavior |
|----------|-----------|----------|
| `createImage` | `(data: CreateNoteImageInput, userId?: string) => Promise<NoteImage>` | Insert one row. |
| `findImagesByNoteId` | `(noteId: string, userId?: string) => Promise<NoteImage[]>` | All images for note with `deletedAt: null`; order by createdAt asc. |
| `findImagesByNoteIdIncludeDeleted` | `(noteId: string, userId?: string) => Promise<NoteImage[]>` | Same but include rows where `deletedAt` is set; for storage cleanup when note undo expires. |
| `findImageById` | `(id: string, userId?: string, includeDeleted?: boolean) => Promise<NoteImage \| null>` | Single image by id. |
| `softDeleteImage` | `(id: string, userId?: string) => Promise<boolean>` | Set `deletedAt = now()`; return true if updated. |
| `softDeleteImagesByNoteId` | `(noteId: string, userId?: string) => Promise<number>` | Set `deletedAt = now()` for all images of the note; return count. |
| `restoreImagesByNoteId` | `(noteId: string, userId?: string) => Promise<number>` | Set `deletedAt = null` for all images of the note; return count. |

**Types:** `CreateNoteImageInput`: noteId, storagePath, fileName, contentType, sizeBytes. No Prisma outside this file.

## 7. Service API: `lib/services/noteImageService.ts`

**Constants:** `MAX_IMAGES_PER_NOTE = 5`, `MAX_IMAGE_SIZE_BYTES = 5 * 1024 * 1024`, `ALLOWED_CONTENT_TYPES = ['image/jpeg', 'image/png', 'image/webp']`, signed URL expiry (e.g. 1 hour).

**Upload limit validation:** The service must enforce **existingImages + newUploads <= 5**. When uploading one or more images, compute current count with `findImagesByNoteId`; then ensure `currentCount + number of new uploads <= MAX_IMAGES_PER_NOTE`. Reject with a stable error (e.g. `IMAGE_LIMIT_REACHED`) if the limit would be exceeded.

**Signed URLs:** Generated in the **service layer** only. `listImagesByNoteId` calls the storage wrapper’s `createSignedUrl(image.storagePath, expiry)` and returns `NoteImageWithUrl[]`.

| Function | Behavior summary |
|----------|------------------|
| `uploadImage(noteId, file, userId?)` | Validate note exists and not deleted. Enforce **existingImages + 1 <= 5**, size ≤ 5MB, contentType in allowlist. Upload to storage, then create metadata. On storage success but DB fail: best-effort storage delete, rethrow. |
| `listImagesByNoteId(noteId, userId?)` | Ensure note exists and not deleted. Repo.findImagesByNoteId; for each image, **service** calls storage.createSignedUrl and returns `{ ...image, url }`. |
| `deleteImage(imageId, userId?)` | **Idempotent.** If already soft-deleted → return. Else delete from storage (404 → success); then **softDeleteImage**. See partial-failure rules below. |
| `softDeleteImagesByNoteId(noteId, userId?)` | When note is soft-deleted; no storage delete. |
| `restoreImagesByNoteId(noteId, userId?)` | When note is restored (Undo). |
| `deleteStorageObjectsForNoteId(noteId, userId?)` | When note Undo **expires**; called from expiry handler. Find all image rows (include deleted); delete each object from storage (404 = success); DB rows stay soft-deleted. |

## 8. Partial failure handling and idempotency

**Priority:** The system prioritizes **correct user-facing state**. The DB is the source of truth for “what images exist”; storage is the medium. After a delete, the user must see the image as gone; metadata must eventually reflect that.

**When storage delete succeeds but DB update fails:**

- Client can retry. Retry is idempotent (metadata may already be updated, or storage may return 404).
- Service: after storage delete, call `softDeleteImage`; if it fails, throw so client can retry.

**When DB update succeeds but storage delete fails:**

- **Still soft-delete the metadata** so the user sees the image as removed (correct user-facing state).
- **Log** the storage deletion failure for operations/debugging.
- Orphan storage objects may remain **temporarily** and can be cleaned up later (e.g. background job or future “orphan cleanup” feature). Do not fail the request in a way that leaves the UI showing the image as still attached.

**Idempotency:**

- **Deleting an image that is already deleted:** Repo returns row with `deletedAt` set → service returns success without calling storage again (or call storage, 404 = success).
- **Deleting a storage object that no longer exists:** Storage client treats 404 as success; proceed to soft-delete metadata (or no-op if already soft-deleted). These cases must **not** cause fatal errors.

---

## 9. Review page behavior

Review page supports **edit mode with Save/Cancel**. Image editing must match note editing:

**In review edit mode, users can:**

- Add images (draft; uploaded on Save).
- Remove newly added draft images immediately (local state).
- Mark existing images for deletion (pendingDelete; applied on Save).

**Nothing is persisted until Save.** Cancel restores the original state (no new uploads, no pending deletes applied). This is the same buffered-edit model as for title, content, and tags.

- **Pattern:** `notes/{noteId}/{uuid}-{sanitizedFileName}`
- **Example:** `notes/a1b2c3.../f4e5d6...-photo.jpg`

**Service interfaces (TypeScript; implement in `lib/services/noteImageService.ts`):**

```ts
// Constants
const MAX_IMAGES_PER_NOTE = 5;
const MAX_IMAGE_SIZE_BYTES = 5 * 1024 * 1024;
const ALLOWED_CONTENT_TYPES = ["image/jpeg", "image/png", "image/webp"];

export type NoteImageWithUrl = NoteImage & { url: string };

export type UploadImageFile = {
  buffer: Buffer;
  fileName: string;
  contentType: string;
  sizeBytes: number;
};

export async function uploadImage(
  noteId: string,
  file: UploadImageFile,
  userId?: string
): Promise<NoteImage>;

export async function listImagesByNoteId(
  noteId: string,
  userId?: string
): Promise<NoteImageWithUrl[]>;

export async function deleteImage(
  imageId: string,
  userId?: string
): Promise<void>;

export async function softDeleteImagesByNoteId(
  noteId: string,
  userId?: string
): Promise<number>;

export async function restoreImagesByNoteId(
  noteId: string,
  userId?: string
): Promise<number>;

export async function deleteStorageObjectsForNoteId(
  noteId: string,
  userId?: string
): Promise<void>;
```

**Storage wrapper (`lib/storage/supabaseStorage.ts`):** `uploadImage(buffer, path, contentType)`, `deleteImage(path)` (treat 404 as success), `createSignedUrl(path, expirySeconds)`.
