# Phase 1 — Milestone 5 Implementation Plan: Image Attachments

**Reference:** `docs/working-mode.md`, `docs/roadmap.md`, `docs/architecture.md`, `docs/milestone-5-design-proposal.md`

---

## 1. Goal (from roadmap)

- Allow visual capture in notes.
- **Features:** Upload images to notes; display image previews inside notes; images stored using Supabase Storage.
- **Assumption:** ~3 images per week per user.
- **Exit criteria:** Users can attach images to notes; images render reliably when viewing notes; basic limits prevent excessive storage usage.

---

## 2. Storage visibility and URL generation

- **Bucket visibility:** **Private.** The Supabase bucket for note images is **private**. Images must **not** be publicly accessible.
- **Image display:** All images are displayed using **signed URLs generated by the server**. The API returns only signed URLs.
- **Where URLs are created:** Signed URLs are generated in the **service layer** (`noteImageService.listImagesByNoteId`), not in the repository. The storage wrapper exposes `createSignedUrl(path, expiry)`; the service calls it and attaches the URL to each image.

---

## 3. Upload during note creation (important)

Users can attach images **before the note is saved**.

**Create flow:**

1. User selects images → stored in **local UI state only** (e.g. `File[]` or draft list).
2. Previews use **`URL.createObjectURL`**; no upload yet.
3. Images are **not uploaded** until the user clicks **Save note**.

**When the user clicks Save note (new note):**

1. Create the note (POST note first).
2. **If note creation fails** → do **not** upload any images; show error.
3. **If note creation succeeds** → upload each draft image, then create `NoteImage` metadata rows.
4. **If note creation succeeds but some image uploads fail** → note remains created; UI reports upload errors (no rollback of the note).

**Edit flow (existing note):** New images added in edit mode are uploaded on Save; same partial-failure rule: note update remains; image upload failures are reported.

---

## 4. Scope for this iteration (minimal)

- **In scope**
  - One **private** Supabase Storage bucket for note images.
  - DB model `NoteImage` for image metadata (soft delete via `deletedAt`).
  - Upload via API (server receives file, uploads to Supabase Storage, creates DB record).
  - List images for a note; return **signed URLs** only (generated in service layer).
  - UI: attach images when creating or editing a note (Notes page); show previews in note card (Notes and Review). Draft images in local state until Save.
  - Limits: max 5 images per note, max 5 MB per image, JPEG/PNG/WebP.
  - Image-level delete: soft-delete metadata + hard-delete storage object; **final**, not recoverable.
  - Note-level delete: soft-delete note and image metadata; storage objects deleted only when Undo window expires (see below).
- **Out of scope**
  - Client-side direct upload to Supabase; upload goes through our API.
  - Image editing, cropping, thumbnails.
  - Auth; optional `userId` on attachment for future.

---

## 5. Image delete behavior

- **During edit:** Existing images can be marked **pendingDelete**; new draft images can be removed immediately from local state.
- **On Save:** For each pending delete: (1) delete storage object (hard delete), (2) **soft-delete** metadata row (`softDeleteImage`). Image-level delete is **final** and not recoverable.
- **Repository naming:** Use **softDeleteImage** and **softDeleteImagesByNoteId** consistently; do **not** hard-delete metadata rows in normal flows.

---

## 6. Note delete behavior and Undo

- **When a note is deleted:** (1) Note row is **soft deleted**, (2) image metadata rows are **soft deleted** (`softDeleteImagesByNoteId`), (3) **storage objects are NOT deleted immediately**.
- **If user clicks Undo within the toast window:** Restore note and restore image metadata (`restoreImagesByNoteId`).
- **If Undo window expires:** Storage objects for that note’s images must be **permanently deleted**. **Undo-expiry cleanup path (explicit):** When the existing client-side Undo timeout fires, the **UI calls a cleanup API** (e.g. `POST /api/notes/[id]/images/cleanup-after-undo-expiry`). **That API invokes `deleteStorageObjectsForNoteId(noteId)`** on the server. After the call, the UI clears the pending-deleted state.

---

## 7. Review page behavior

Review page has **edit mode with Save/Cancel**. Image editing must match note editing:

- In **review edit mode**, users can: **add images**, **remove new draft images** (immediately from local state), **mark existing images for deletion** (pendingDelete).
- **Nothing is persisted until Save.** Cancel restores the original state (no new uploads, no pending deletes applied).

---

## 8. Invariants to protect

- **Layering:** No Prisma in API routes; no business logic in UI beyond state and API calls. Storage logic in `lib/storage`; DB access in repositories; business logic in services. **Signed URLs are generated in the service layer.**
- **Soft delete:** Notes and image metadata use `deletedAt`; default reads exclude soft-deleted. Storage objects are not deleted on note soft-delete; they are deleted when note Undo expires or on image-level delete.
- **Multi-user readiness:** Optional `userId` on `NoteImage`; repositories accept `userId?: string`.
- **Review and existing behavior:** Review batch stability, tag behavior, and review-event semantics unchanged. Image attachment is additive.

---

## 9. Upload limit validation

Service must enforce: **existingImages + newUploads <= 5** (not only existing count). When uploading one or more images, compute current count with `findImagesByNoteId`, then ensure `currentCount + number of new uploads <= MAX_IMAGES_PER_NOTE`.

---

## 10. Idempotency

- **Delete image:** Deleting an image that is already deleted, or deleting a storage object that no longer exists, must **not** cause fatal errors. Operations are **idempotent** (already soft-deleted or storage 404 → success).

## 12. Technical decisions (fixed)

1. **Bucket visibility:** **Private.** Images accessed only via **signed URLs** generated by the server (in the service layer).
2. **Max images per note:** 5; validation uses **existingImages + newUploads <= 5**.
3. **Max file size:** 5 MB per image.
4. **Allowed MIME types:** image/jpeg, image/png, image/webp.
5. **Metadata delete:** Always **softDeleteImage** / **softDeleteImagesByNoteId**; no hard-delete of metadata in normal flows.
6. **Naming:** `NoteImage`, `noteImageRepository`, `noteImageService`.
7. **Upload API shape:** **Single-file-per-request.** `POST /api/notes/[id]/images` accepts one multipart file per request; the UI loops and calls the API once per image to upload multiple images.

## 13. Required smoke test

- **API smoke test** (extend `scripts/smoke-api.ts`): Create note → upload image(s) → GET list (assert signed URLs in response) → DELETE image → GET list empty or reduced. Optionally assert upload fails when limit exceeded or invalid type/size.
- **Manual UI checklist:** Create note with images (draft then Save); edit note add/remove images; view on Notes and Review; note delete → Undo restores images; note delete → Undo expiry (wait or shorten timer in dev) → storage cleanup; image-level delete is final; limits (5 images, 5 MB) enforced.

## 15. What would break if we changed X

- Storage path convention change → existing records point to wrong objects; migration or backfill needed.
- Making bucket public → security and design doc mismatch; keep private + signed URLs.
- Removing per-note limit → storage growth; keep or replace with per-user quota later.
- Hard-deleting image metadata → breaks soft-delete and Undo semantics; keep softDeleteImage.
